# RAG 企业知识库实验方案

日期：2026-11-01。状态：实验设计，尚未执行。指标定义见 [METRICS.md](METRICS.md)。本文中的样本数、参数和判定门槛是预先设计，不是实测成绩。

## 1. 这次要回答什么

核心问题是：**混合检索、重排和自适应纠错，是否让用户更容易获得正确且有依据的答案，增加的耗时与成本是否值得？**

拆成三个可验证的问题：

1. 加入 BM25 后，是否找回了纯向量检索漏掉的术语、型号、数值和相似主题证据？
2. 加入 reranker 后，是否把候选中的有效证据排到前面，让最终 Top-5 更有用？
3. 加入自适应流程后，是否修复了回答错误、遗漏或无依据结论，同时没有大量误拒答？

实验分两层：先用受控实验解释模块贡献，再用真实 API 比较应用效果。历史 BGE-small 50 题结果仅作为参考，不能与新实验直接相减后宣称提升。

## 2. 先明确当前代码能做什么

检查现有实现后，有以下执行边界：

- `classic` 并不等于纯向量检索。它会按快照选择混合索引，还会调用 reranker；复合问题也可能先拆分，并执行上下文扩展。
- `/ask` 目前没有独立关闭 BM25、重排、问题拆分或上下文扩展的请求参数。不能仅切换 `mode` 就声称做了模块消融。
- 混合检索当前为 Dense/BM25 各取 `candidate_k`，以 `RRFRanker(k=100)` 融合，再返回 `candidate_k` 条。
- `top_k=5` 是种子证据数量，上下文扩展后可超过 5 条；当前扩展函数默认限制为 18 条、14000 字符、邻页半径 1。必须记录真正送进模型的材料。
- 回答服务当前返回的 `usage` 为空，API 响应也没有完整 token 用量；需补采集才能统计真实调用成本。
- `evaluate_rag.py` 保存的聚合检查存在 `1.0 is True` 问题，错误记录还缺耗时。应先修复后再统计；人工质量判定不能只依赖这个聚合字段。

因此，以下 A/B/C 需要新增离线实验驱动及模块开关；真实 API 的 classic/agent/adaptive 比较可复用现有入口。新增驱动应复用项目检索和回答代码，避免另写一套行为不同的 RAG。

## 3. 数据怎么准备

### 3.1 固定语料

以已有 100 篇 Markdown 的清单为起点，冻结文件内容和 SHA-256，导入专用实验知识库。所有正式组使用同一套应用分块、相同活动快照和 BGE-large 向量。

导入后保存实际文档数、块数、分块参数、模型名称、维度和快照 ID。新链路块数以实际产物为准，不能强行沿用历史脚本的 634 块。主实验不同时更换分块策略或 embedding 模型，避免无法解释提升来源。

### 3.2 数据集规模与划分

| 数据集 | 数量 | 用途 |
|---|---:|---|
| 开发集 | 现有 50 题，逐题人工复核 | 调参数、排查已知失败、验证采集和评分流程 |
| 冻结测试集 | 新增 100 题 | 正式比较，冻结后不用于调参 |
| 扩展集 | 后续另建 | 多轮、PPTX/图表、联网和大规模测试，不混入本轮总体成绩 |

测试集按一个主要类别计数，额外特征可以多标签：

| 主要类别 | 数量 | 出题要求 |
|---|---:|---|
| 单文档直接事实 | 25 | 原文有明确答案，覆盖概念、条件、过程 |
| 术语、型号、数值 | 20 | 需要精确实体或单位，检验关键词召回能力 |
| 相似主题辨析 | 15 | 库中存在易混淆材料，但能根据限定条件确定答案 |
| 跨文档综合 | 20 | 至少两个来源共同支持答案，单一来源不完整 |
| 无答案 | 20 | 10 道领域相关但材料缺失，5 道错误前提，5 道无法消解的冲突 |
| 合计 | 100 | 80 道可回答，20 道应拒绝给出确定结论 |

无法消解的冲突题允许明确说明冲突并引用双方材料；不要求只输出一句“无法回答”。若证据可以确定时间、对象或条件差异，应归为可回答辨析题。

尽量让新题使用现有 50 题未覆盖的来源；若跨文档题不可避免重用来源，必须排除相同事实、近义改写和同证据片段。按来源及证据重叠分组检查泄漏，保存重用情况。100 题适合建立项目基线，不能据此证明所有企业场景的稳定效果；无答案题只有 20 道，单题就影响该类别 5 个百分点。

### 3.3 每题标什么

保存 `question_id`、`split`、主要类别、问题、`answerable`、标准答案、必要答案要点、原文逐字证据、来源/快照/块 ID、相关性等级、无答案原因和审核记录。

跨文档题应为每个必要要点标出可替代的证据组：同一要点可由多个块之一支持，不要求把所有等价块都召回。除排名指标外，额外计算“必要要点证据覆盖率”，判断是否覆盖了完整推理所需材料。

人工先核对原文，再审核 A/B/C 在开发流程或冻结检索配置下返回的候选池，给候选标记 0=无关、1=部分支持、2=直接支持。标注时隐藏组别。相关块按等级至少为 1 计入二值检索指标，等级用于 nDCG。

候选池通常不是全库穷尽标注，因此 Recall 必须注明“基于已标注相关集”；各组正式 Top-10 若有未判定块，先补做盲审后统一计分，不能直接把未判定块当作无关。对无答案题需检索全库核对：没找到证据不自动等于确定无答案，无法确认的题先剔出并在冻结前补足。

最好由两人独立审核答案和无答案结论，分歧复核；只有一人时，应明确单人标注并隔时复查，不宣称人工一致性已验证。所有题在正式运行前冻结；错误标签的修订必须记录原因，对所有组统一重算。

## 4. 第一层：控制变量，验证检索和重排

| 组别 | 候选获取 | 排序与输入回答的证据 | 验证目的 |
|---|---|---|---|
| A：Dense | BGE-large Dense Top-20 | 原始排序前 5 条 | 基线 |
| B：Hybrid | Dense Top-20 + BM25 Top-20，RRF 融合取 20 | 融合排序前 5 条 | B−A：混合检索整体贡献 |
| C：Hybrid + rerank | 与 B 完全相同的 20 条候选 | reranker 排序前 5 条 | C−B：重排贡献 |

固定设置：

- 所有组读取同一个混合集合中的向量与文本，使用相同快照过滤；A 只查询 Dense 字段，避免另一个集合带来的差异。
- 单次原始问题检索，关闭问题拆分、查询改写、邻页扩展和联网。
- 不使用分数阈值过滤。余弦、RRF 和 reranker 分数不能直接使用同一个 0.3 阈值；按排名截取，少于 5 条如实记录。
- 生成使用相同模型、温度 0、系统提示词和输出长度限制，回答原始问题，保留来源编号；最多 5 条证据、14000 字符，按固定顺序整块纳入，并记录预算导致的丢弃。
- C 直接复用 B 的候选记录，再执行重排，确保候选一致。

混合检索使用两路检索，计算量大于 A；这不是严格等算力比较。主实验比较“增加这套检索能力是否值得”，同时报告检索耗时。若需要解释增加候选预算的影响，追加 Dense Top-40 的独立对照，不改变主结果。

先在 80 道可回答测试题上做纯检索评分，再对全部 100 题生成回答。检索排名保存到 Top-20，报告 Recall@20、Recall@5、MRR@10、nDCG@5；跨文档题另报必要要点证据覆盖率。无答案题不进入召回率均值。

直观解释：如果 B 的 Recall@20 高于 A，说明候选池找回了更多证据；如果 C 的 nDCG@5 高于 B 而 Recall@20 不变，说明重排把已有证据排得更靠前。如果检索变好而答案没变好，下一步应检查提示词、上下文预算或生成，而不是继续堆检索模块。

## 5. 第二层：真实应用是否更好用

| 组别 | 运行入口 | 解释范围 |
|---|---|---|
| P | 真实 API，`mode=classic` | 当前经典完整链路 |
| Q | 真实 API，`mode=agent` | 相对 P 增加路由、相关性判断和前置纠错流程 |
| R | 真实 API，`mode=adaptive` | 相对 Q 增加生成后的依据/有效性检查及后续纠错 |

三组使用同一个知识库和测试集，`candidate_k=20`、`top_k=5`、`allow_web=false`；`min_score` 在开发集选定后冻结，三组一致。保留当前问题拆分与扩展行为，记录实际查询数、上下文数和长度。纠错预算拟设为最多 2 次改写、3 次生成，正式运行前核实运行配置确实生效。

每题独立，不复用会话历史。该实验只验证单轮知识问答，不声称覆盖多轮能力。P 与 C 不等价，不能把 P−C 单独归因于某一个模块。

主看 R−P 的最终答案与成本变化；Q 是解释中间机制的辅助组。Q/P、R/Q 的结论是对应流程整体的效果；若要进一步宣称“查询拆分单独提升多少”，需要额外开关和专门对照。

尤其要记录：P 错/R 对、P 对/R 错、两者均错的题数，以及“通过改写找回证据”“通过重新生成修复答案”“误拒答”等原因。执行了纠错节点不代表纠错有效。

## 6. 怎么评分，什么是主要结论

### 6.1 主要质量指标

**主要指标：可回答题的端到端正确率 = 正确完成的题数 / 全部 80 道可回答题。** 请求失败、超时、拒答均计未正确完成；另报有效响应上的条件正确率，避免隐藏服务失败。

人工评分规则在看输出前固定：全部必要要点正确、无实质错误，才计正确。部分正确单独标记用于诊断，不计满分。隐藏组别与系统名称，随机呈现答案；按题配对比较结果。

护栏指标为：无答案题正确拒答率、可回答题误拒答率、引用支持率、引用覆盖率和请求失败率。正确拒答需人工确认答案没有偷偷编造确定性结论，不能只看 `status`。当前 classic 可能在有 evidence 时标记 `answered`，即使答案文本实际拒答。

### 6.2 辅助指标

- RAGAS 三项评分用于解释事实支撑、上下文覆盖和相关性。主表在可回答题上报告，另列有效评分数；无答案题单独按拒答口径评估，不给空参考答案强算 Context Recall。
- 评审使用固定模型、版本、提示和 embedding 配置；尽量独立于生成模型，若使用同一模型则披露评审偏差。人工主指标不依赖模型自评。
- RAGAS 必须使用真正送给最终回答生成的上下文。自适应系统最终拒答时可能返回空 `sources`，因此需额外留存中间候选和最后一次生成上下文，不能用最终空来源倒推检索失败。
- 评分异常不是质量得 0；保留异常及完整率。正式主张模型评分差异前先解决缺失值，无法解决则明确评分不完整。

### 6.3 如何判断改动值得保留

建议在开发阶段结束时预先确认以下项目决策规则，确认后不能看测试结果再改门槛：

1. R 相对 P 的可回答题端到端正确率至少提高 5 个百分点，即 80 题至少净增 4 道正确答案。
2. 无答案题正确拒答数不下降；引用支持率不下降；报告实际计数与不确定性，不把小样本的“不下降”当作总体保证。
3. 热启动 P95 不超过 P 的 2 倍，平均每题 LLM 调用次数不超过 P 的 3 倍。若超出，单独讨论是否以延迟换质量，不直接宣布全面优于基线。

以上是拟议的项目取舍门槛，不是行业标准或既定 SLA。对 A/B、B/C、P/R 的主要差值按题分层配对 bootstrap 10000 次，固定随机种子 20261101，报告 95% 置信区间；来源高度重叠时追加按来源组重采样的敏感性分析。区间包含 0 时表述为“本样本点估计提高，但证据不足以确认稳定提升”。其余比较视为探索性，不挑最好看的结果作为唯一结论。

## 7. 性能和成本怎么测

质量实验先每题每组运行一次，温度 0；这不保证模型输出完全确定。另预先从开发集固定 20 道代表题，P/R 各重复 3 次检查波动，结果不混入冻结测试集成绩。

性能测试与 RAGAS 评审分开运行：

1. 记录 CPU/GPU、内存、系统、服务部署位置、模型版本、网络路径和进程配置。
2. P/R 各做 10 次不计入统计的预热请求；随后每组每个并发档位至少 100 次请求，分两轮执行并保留轮次。使用相同问题序列，组别交替运行，避免全部先测一个组。
3. 从并发 1 开始，再测并发 2、4；遇到明显超时或拒绝服务则停止升档，保存结果。明确采用固定并发的闭环负载，客户端时间包含等待；服务返回 busy 也计失败。
4. 成功响应报告 P50/P95/最大值、吞吐；失败响应另报耗时、失败率和错误类型。该请求规模的 P99 不稳定，若要声明尾延迟，应扩至至少 1000 次并说明负载条件。
5. 冷启动单独重启实验服务测量模型加载与首请求，不与热启动数据混合；不重启用户其他服务。

采集每次生成、判断、拆分和改写调用的输入/输出 token、耗时、重试和用途。平均每题成本包含失败尝试，离线评审费用单列。服务商不返回 usage 时标为缺失，不用空字典当作零成本；只有本地 tokenizer 估算时必须标为估算值。

## 8. 执行顺序与产物

| 阶段 | 具体工作 | 完成条件 |
|---|---|---|
| 0：准备 | 记录代码版本/未提交差异；检查服务健康；导入专用知识库、核对快照；修复回归聚合和错误计时 | 10 道开发题能获得可审计记录，包含失败样本演练 |
| 1：标注 | 复核旧 50 题，新增并审核 100 道测试题，保存证据与泄漏检查 | 测试集冻结，有版本和摘要 |
| 2：实验支持 | 新增 A/B/C 驱动、候选保存、真实上下文及 usage/阶段耗时采集 | 同一题可重放，B/C 候选一致，开关与参数可查 |
| 3：开发调优 | 只在开发集调整阈值和纠错预算，冻结运行配置与判定规则 | 不再根据测试结果改参数 |
| 4：正式质量 | 测试集运行 A/B/C/P/Q/R，盲审、模型评分、按题配对汇总 | 全部预定题有结果或明确错误，无静默删题 |
| 5：性能成本 | P/R 压测、波动检查、成本汇总 | 延迟/失败/费用可追溯至原始请求 |
| 6：报告 | 汇总表、差值区间、成功/退化样例、限制与下一步 | 原始证据能复核每个结论 |

建议产物目录（待创建）：

  calls.jsonl            # 各次模型调用的用途、耗时、token
  human-review.csv       # 隐藏组别的人工评分及复核记录
  ragas-scores.csv        # 模型评分与异常

现有 API 冒烟命令如下，需先准备真实知识库 ID 和经过适配的数据集；不是 A/B/C 消融命令：

```powershell
python -m scripts.evaluate_rag `
  --knowledge-base-id <实验知识库ID> `
  --dataset <开发集JSONL路径> `
  --output <输出JSON路径> `
  --mode classic
```

将 `--mode` 改为 `agent` 或 `adaptive` 可运行另外两种应用模式。数据集每行若自带 `mode` 会覆盖命令行选项，所以比较时移除该字段或严格核对。跨文档测试不要传 `--document-id`。A/B/C 驱动和新采集功能尚未实现，不提供不存在的 CLI 参数。

## 9. 预计工作量与最终呈现

主实验为 6 组 × 100 题 = 600 次题目运行；这不是 600 次 LLM 调用，自适应判断和重试会额外调用。性能计划为 2 组 × 3 档并发 × 100 次 = 600 次请求，另加预热、60 次/组的波动检查和离线评分。先用 10 道开发题估算各组调用量，再乘计划题数估算预算，未取得真实用量前不承诺费用或完成时长。

资源有限时，先完成 A/B/C 的纯检索比较和 P/R 的 200 次质量请求；这是阶段性结论。尚未运行的 A/B/C 生成、Q、性能档位必须标为待完成，不能把缩减版写成完整实验。

最终报告至少给出以下两张表，所有空值填“未测”，不要填预期数字：

| 组别 | Recall@20 | nDCG@5 | 正确完成/80 | 正确拒答/20 | 引用支持率 | 请求失败数 |
|---|---|---|---|---|---|---|
| A/B/C/P/Q/R 分别列行 | 未测 | 未测 | 未测 | 未测 | 未测 | 未测 |

P/Q/R 的多次检索需明确报首轮排名，最终证据另报覆盖率；不能把多轮结果拼成一个虚构的 Top-K。没有相应采集的字段填写未测。
